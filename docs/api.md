# Revflare REST API v1

Base: `https://<host>/api/v1`. JSON in and out; errors are `{ "error": "message" }` with a 4xx/5xx status. Types: `shared/types.ts`.

On the Workers Free plan the database has daily limits (5M rows read, 100k written; reset at 00:00 UTC). When they are hit the API answers `503 { code: "quota" }`; imports that would use up the background share answer `429 { code: "budget" }` (backfills pause and resume by themselves).

## Authentication

| Client | How |
| --- | --- |
| Web app | Session cookie `rf_session` from `POST /auth/login` (browser mutations must be same-origin). |
| iOS app | `Authorization: Bearer rfd_...` from `POST /auth/pair` (QR code) or `POST /auth/device` (email + password). Sliding one-year expiry. The app can also sign a browser in (`/auth/app-login`). |
| CLI, MCP, other tools | `Authorization: Bearer rf_...` workspace API key (`POST /api-keys`). Bound to one workspace. |

Sessions and device tokens pick the workspace from `X-Workspace-Id`, else the last one used, else the first. Roles: `owner` (everything), `admin` (all but deleting the workspace), `viewer` (read). Instance admins act as owner everywhere.

## Auth (public)

- `GET /auth/status` → `AuthStatus` `{ setup, authenticated, setupToken?, magicLink?, appLogin?, pushLogin?, appStoreUrl? }` (`magicLink: true` when sign-in links by email are on: `EMAIL` binding + `EMAIL_FROM` set and turned on in Admin → Settings; `appLogin: true` when an iOS device is signed in on the instance, `pushLogin: true` when APNs is configured and a signed-in device has push; `appStoreUrl` from the optional `APP_STORE_URL` var).
- `POST /auth/setup` `{ name, email, password, workspaceName?, currency?, setupToken? }` — first user only.
- `POST /auth/login` `{ email, password }` → cookie.
- `POST /auth/magic-link` `{ email }` → `{ ok }`: emails a one-time sign-in link `<origin>/auth/link#<token>` (15 minutes) to an existing active account, sent after the response; the answer is the same for unknown accounts. `400` for an invalid email, `404` when sign-in links are off, `429` after 3 requests per email or 10 per IP in 15 minutes.
- `POST /auth/magic-link/verify` `{ token }` → `{ ok }` + cookie. Works once; the user's other open links end. `400` invalid, used or expired; `403` disabled account; `404` when sign-in links are off (turning them off ends outstanding links).
- `POST /auth/device` `{ email, password, deviceName? }` → `DeviceTokenResponse` `{ token, user, workspace, server }`.
- `POST /auth/pair` `{ code, deviceName? }` → `DeviceTokenResponse`. Codes come from `POST /pairing-codes`, expire after 10 minutes and work once.
- `POST /auth/logout` — with a device token: deletes the token and its push registrations.

### Sign in on the web with the iOS app (`/auth/app-login`, see `docs/app-login-spec.md`)

A *web login request* lives 3 minutes and works once. The browser keeps a poll secret; the iOS app (device token of
the user's own device, active account) approves.

- `POST /auth/app-login` `{ kind?: "qr" }` → `WebLoginStart` `{ id, secret, qr, expiresAt }`; `qr` is
  `revflare://web-login?s=<server>&r=<id>&k=<nonce>` (the page shows it as a QR code; the secret is never in it).
- `POST /auth/app-login` `{ kind: "push", email }` → `{ id, secret, number, expiresAt }`: pushes (category
  `WEB_LOGIN`, custom `{ type: "web_login", id }`, expiring with the request) to the devices of that account; the page
  shows `number`. The answer is the same for unknown, disabled or push-less accounts. `404` without APNs, `400` for an
  invalid email. Starts are limited to 10 per IP and 3 per email (push) in 10 minutes (`429`); browser calls must be
  same-origin.
- `GET /auth/app-login/:id` with `X-Login-Secret: <secret>` → `WebLoginPoll` `{ status }`: `pending`, `denied`,
  `expired`, `consumed`, or once, when approved, `{ status: "signed_in", workspaceId? }` with the session cookie (the
  workspace the approving app is on). `403` if the account was disabled meanwhile; `404` for a wrong secret.
- `DELETE /auth/app-login/:id` (secret header) → `{ ok }`: cancels.
- `POST /auth/app-login/:id/inspect` `{ nonce? }` (device token) → `WebLoginInfo`
  `{ kind, ip, city, country, browser, os, createdAt, expiresAt, numbers? }`. QR requests need the nonce from the code;
  push requests must be for the device's user and come with `numbers` (the right one and two others, shuffled).
- `POST /auth/app-login/:id/approve` `{ nonce?, number? }` (device token) → `{ ok }`. A wrong `number` denies the
  request (`403`).
- `POST /auth/app-login/:id/deny` `{ nonce? }` (device token) → `{ ok }`.
- App endpoints: `401` without a device token (web sessions and API keys cannot answer), `404` for unknown ids, a
  wrong nonce or another user's push request, `410` when the request expired or was already answered.
- `GET /auth/invitations/:token` → `{ email, role, workspaceName, newWorkspace, newWorkspaceName, isAdmin }` (what a pending invitation link is for; 404 when invalid or expired).
- `POST /auth/invitations/accept` `{ token, name?, email, password }` → `{ ok, workspaceId }`. Invitations without a workspace (instance invitations) create one with the invitee as owner; `isAdmin` invitations make them an instance admin. Disabled accounts cannot accept.
- `GET /version` (public) → `{ version, commit, apiVersion }`.

## Account

- `GET /me` → `Me` (user with `dailyDigestEmail`, current workspace + permissions, all workspaces, auth kind, version, `features.push`, `features.email` = Email Sending configured).
- `PATCH /me` `{ name?, dailyDigestEmail? }` (at least one; `dailyDigestEmail`: the daily digest email, sent only when email is configured, not with an API key), `POST /me/password` `{ current, password }`.
- `GET /workspaces`, `POST /workspaces` `{ name, currency }` (instance admin), `PATCH /workspace` `{ name?, currency? }`, `DELETE /workspace`.
- `GET /members`, `POST /invitations` `{ email?, role }` → `{ url, expiresAt }`, `GET /invitations` (pending), `DELETE /invitations/:id`, `PATCH /members/:userId` `{ role }`, `DELETE /members/:userId`.
- `GET /api-keys`, `POST /api-keys` `{ name }` → `{ id, name, token }` (shown once), `DELETE /api-keys/:id`.
- `POST /pairing-codes` (web session only) → `PairingCode` `{ code, url: "revflare://pair?server=...&code=...", expiresAt }`.
- Devices (the caller's own): `GET /devices`, `POST /devices` `{ apnsToken, environment: "production"|"sandbox", name?, prefs? }` → `Device`, `PATCH /devices/:id` `{ prefs?, activityToken?, widgetToken? }` (`prefs.appOverrides`: `{ [appId]: { muted?, sales?, renewals?, trials?, refunds?, cancellations?, alerts?, funnelAlerts? } }`, per-app settings over the global kinds; `muted` silences the app) (Live Activity / WidgetKit push tokens, hex; `null` when they end), `DELETE /devices/:id`, `POST /devices/:id/test`.
  `DevicePrefs`: `sales, renewals, trials, refunds, cancellations, alerts, funnelAlerts, dailySummary, weeklySummary` (booleans; `alerts`: revenue-side alerts, `funnelAlerts`: event silence / funnel anomaly / release regression, push kind `funnel`, default on), `minUsd`, `apps` (ids or null), `sound` (`cash`|`default`|`none`), `quietStart`/`quietEnd` (`"23:00"`), `timezone` (IANA), `locale`, `pushVersion` (set by the iOS app: the push texts its build knows; `1` = funnel alert pushes and the daily summary's digest line, which builds without it (0) do not get; `2` = sale / trial pushes of Apple Ads purchases name the source: `PUSH_BODY_SALE_ADS` (product, country, amount, "Apple Ads · <ad group name or #id>", the campaign when there is no ad group) for new subscriptions, purchases, renewals and conversions, `PUSH_BODY_TRIAL_ADS` (product, country, source) for trials; not for Apple's test attribution; older builds keep `PUSH_BODY_SALE` / `PUSH_BODY_TRIAL`; `3` = the "notifications silent" alert of an Android app says Google Play (`PUSH_BODY_ALERT_SILENT_PLAY`), older builds get `PUSH_BODY_ALERT_SILENT`; `4` = goal-reached pushes (push kind `goal`, for goals with `notify`, once per period: title `PUSH_TITLE_GOAL` with the goal's name, or `PUSH_TITLE_GOAL_<METRIC>` for an unnamed goal, body `PUSH_BODY_GOAL_REACHED` (current value, target); payload `goalId`), which older builds do not get).

## Instance administration (`/admin`, instance admins)

Instance admins only, with a web session or a device token (`rfd_...`, e.g. `revflare login --email`): workspace API keys always get `403`, even an admin's. Responses are `cache-control: no-store`.

- `GET /admin/overview` → `AdminOverview`: `counts` (users, active / disabled users, admins, users active in the last 30 days, workspaces, apps, archived apps, API keys, iOS devices), `sales` (purchases all time and in 30 days, 30-day revenue in USD, from the daily rollups `workspace_daily`: `transactions` is never scanned), `recentSignups`, `recentLogins`, `jobs` (queued, running, failed in 7 days + the last 5 failures), `alerts.open`, `cron` (last 5-minute tick, `stale` after 15 minutes without one), `usage` (as `/admin/usage`), `version`, `update` (as `/admin/updates`).
- `GET /admin/usage` → `AdminUsage`: database size, today's background row budget, Free plan limits.
- `GET /admin/users` → `{ items: AdminUser[] }` (`id, name, email, isAdmin, status: "active"|"disabled", createdAt, lastLoginAt, workspaces: [{ id, name, role }]`).
- `PATCH /admin/users/:id` `{ name?, isAdmin?, status?: "active"|"disabled", resetPassword?: true }` → `AdminUser` (with `password`, shown once, after a reset). Disabling or resetting the password ends the user's web and iOS sessions (and push registrations); a disabled user's API keys are refused until they are enabled again. `409` when the instance would lose its last active admin, or when disabling the only owner of a workspace; `403` for disabling yourself.
- `DELETE /admin/users/:id` — deletes the account, memberships, sessions, devices and API keys (workspace data stays). `403` for yourself; `409` for the last active admin, and for the only owner of a workspace (`"<name> is the last owner of "<workspace>". Make someone else owner or delete the workspace first."`).
- `GET /admin/workspaces` → `{ items: AdminWorkspace[] }` (`id, name, currency, createdAt, members, owners: [{ id, name, email }], apps, apiKeys`).
- `POST /admin/workspaces` `{ name, currency?, ownerEmail? }` → `201 AdminWorkspace`. The owner is an existing user (`404` otherwise: invite them instead), default the caller.
- `DELETE /admin/workspaces/:id` — the workspace and all of its data (as `DELETE /workspace`).
- `GET /admin/invitations` → `{ items: AdminInvitation[] }`: every pending invitation (`workspaceId`/`workspaceName` + `role`, or `newWorkspaceName` for a workspace of their own; `isAdmin`).
- `POST /admin/invitations` `{ email?, workspaceId?, role?, newWorkspaceName?, isAdmin? }` → `201 { id, url, expiresAt }`. With `workspaceId` the invitee joins it as `role` (default `viewer`; `409` if `email` is already a member); without it they get a new workspace (named `newWorkspaceName`, default "<name>'s apps") as owner. Links work once and expire after 7 days.
- `DELETE /admin/invitations/:id`.
- `GET /admin/updates` → `UpdateStatus` `{ current, commit, latest, updateAvailable, url, publishedAt, checkedAt, status, message, enabled, repo }`. `status`: `ok`, `not_found` (GitHub answers 404: the repository is missing or private), `error` (the last known release is kept), `never`, `disabled`. The cron asks GitHub (`/repos/<repo>/releases`, highest `v<x.y.z>` tag that is not a draft or prerelease) once a day (6 hours after an error). Env: `UPDATE_CHECK="false"` turns it off, `UPDATE_REPO` (`owner/name`) replaces `FerdiKT/revflare`.
- `POST /admin/updates/check` → `UpdateStatus` after asking GitHub now (a result from the last minute is returned as is; `409` when turned off).
- `GET /admin/email` → `AdminEmailSettings` `{ configured, from, enabled }`: `configured` when the `EMAIL` send_email binding and `EMAIL_FROM` exist; `enabled` when sign-in links by email are on (instance setting `magic_link_enabled`, off by default).
- `PATCH /admin/email` `{ enabled }` → `AdminEmailSettings`. `400` when turning on while email is not configured (Cloudflare Email Sending to any address needs Workers Paid and an onboarded domain). Turning off ends every outstanding link.
- `POST /admin/email/test` → `{ ok, to }`: sends a test email to the signed-in admin right away; `502 { error }` with Cloudflare's message and code when sending fails, `400` when not configured.

## Apps and setup (`manage` to change)

- `GET /apps` → `{ items: App[], currency }` (sorted by 28-day revenue; `metaEnabled` = Meta Ads integration on, `refundRequestsEnabled` = answers to Apple's refund requests on). `GET /apps/:id` → `App & { products: Product[], acquisition: AcquisitionStatus }`.
- `App.platform`: `ios` (App Store), `android` (Google Play, `bundleId` = the package name, `revflareNotificationUrl` = the RTDN push URL, `googlePlay` = `{ rtdnUrl, configured, pushAuth, lastCheck }`; see [Google Play](#google-play-android-apps)) or `web` (a website selling through Polar, `revflareNotificationUrl` = the Polar webhook URL, `polar` = `{ webhookUrl, connected }`; see [Polar](#polar-web-apps)). An iOS and an Android app may share the bundle id / package name.
- `POST /apps` `{ name, bundleId, appleAppId? }` (iOS), `{ platform: "android", name, packageName }` (Google Play) or `{ platform: "web", name, bundleId? }` (Polar), `PATCH /apps/:id` `{ name?, commissionPct?: 15|30, archived?, rcProjectId?, forwardNotificationUrl?: string|null, platform?: "web" }` (`platform: "web"` only for an iOS app without an App Store id or transactions). With `forwardNotificationUrl` (https, e.g. the app's RevenueCat Apple server notification URL) every verified App Store notification is also POSTed unchanged to that URL after Revflare answers Apple (one retry; last result in `App.forwardStatus`).
- `POST /apps/import` `{ setUrls: "empty"|"none", only?: [bundleId|appleId] }` — imports apps from App Store Connect; `empty` points apps without a notification URL at Revflare (URLs pointing elsewhere are left alone).
- `POST /apps/sync-products` `{ appIds? }` — product names and periods from App Store Connect.
- `POST /apps/:id/connect-notifications` — replaces the app's notification URL with Revflare's; a URL it replaces (e.g. RevenueCat's) becomes the app's `forwardNotificationUrl`, so that service keeps receiving every notification.
- `POST /apps/:id/test-notification` `{ environment: "Sandbox"|"Production" }` — Apple sends a TEST notification.
- `POST /apps/:id/sync` — one round of Notification History + Transaction History now.
- App Store only (`400` "… is App Store only" for Android and web apps): `connect-notifications`, `test-notification`, `sync`, `POST /imports/apple`, `PUT /apps/:id/offers`, `POST /apps/:id/offers/import`, `PUT /apps/:id/integrations/refunds`; Android apps get no App Analytics acquisition (`GET /apps/:id` has no `acquisition`) and no Apple Ads attribution.
- Credentials: `GET /credentials`, `POST /credentials` (`{ kind: "appstore_iap"|"appstore_connect"|"appstore_reports", name, keyId, issuerId, privateKey, vendorNumber? }`, `{ kind: "revenuecat", name, apiKey: "sk_...", projectId }` or `{ kind: "google_play", serviceAccount: <service account JSON key file>, name? }` (stored encrypted; `keyId` = `private_key_id`, `issuerId` = `client_email`, `config` `{ clientEmail, projectId }`)), `PATCH /credentials/:id` `{ vendorNumber?, name? }`, `DELETE /credentials/:id`.
  `appstore_reports` is an optional App Store Connect key used only for reports (Sales and Trends, App Analytics), e.g. one with the Sales role: reports try it first, then the `appstore_connect` key (on 401/403). The vendor number may sit on either.

## Google Play (Android apps)

Setup, mapping and limits: [google-play.md](google-play.md).

- `GET /apps/:id/google-play` (`read`) → `GooglePlaySettings` `{ appId, packageName, rtdnUrl, pushServiceAccount, credential: { id, name, clientEmail, projectId, appSpecific } | null, lastNotificationAt, lastCheck: { at, ok, error? } | null, voidedCheckedAt }`; `400` for iOS apps.
- `PUT /apps/:id/google-play` (`manage`) `{ serviceAccount?: <JSON key file (string or object)>, credentialId?: string|null, pushServiceAccount?: string|null }` → `GooglePlaySettings`. `serviceAccount` stores a new `google_play` credential and makes it the app's (else the workspace's newest `google_play` key is used); `pushServiceAccount` = the service account of the Pub/Sub push subscription: when set, every push must carry its OIDC token.
- `POST /apps/:id/google-play/test` (`manage`) → `{ ok, error? }`: a read-only Play Developer API call (voided purchases of the last hour, which needs the financial permission).
- `POST /apps/:id/google-play/voided` (`manage`) → `{ apps, requests, refunded, errors }`: polls voided purchases (refunds) now; the cron does it once a day per Android app (03:00–06:00 UTC, background budget).
- `POST /google/rtdn/:key` (public; Pub/Sub push endpoint, `key` = the app's secret): body `{ message: { data: base64(DeveloperNotification), messageId, publishTime }, subscription }`. With a push service account set, `Authorization: Bearer <OIDC JWT>` is verified (RS256 against Google's certificates, issuer `accounts.google.com`, audience = the push URL, `email` = the push service account, `email_verified`, not expired) → `401` otherwise. Deduplicated on `messageId` (stored as event uid `gp:<messageId>`; a duplicate answers `{ ok, duplicate: true }` without calling Google). `200 { ok, ignored }` for pending purchases (nothing stored until paid), unknown purchase tokens and `pendingRefundReviewNotification` (logged); `503` while the app has no service account or Google answers 401/403/5xx (Pub/Sub retries with backoff for up to 7 days). Another package's notification and malformed bodies answer `200 { ok, ignored }` too (logged; another package raises a `google_play_package` alert once a day), since Pub/Sub would retry a `4xx` for 7 days.
- `Transaction.store`: `app_store` | `play_store` | `polar` (`source`: `apple`, `revenuecat`, `google_play` or `polar`). `Subscription.cancelReason` (Google Play): `user[:<cancel survey reason>]`, `system`, `developer`, `replacement`. `Overview.topApps[].platform`. Alert kind `google_play_test` (info): a Play Console test notification reached the app's RTDN URL.

## Polar (web apps)

Setup, mapping and limits: [polar.md](polar.md).

- `GET /apps/:id/polar` (`read`) → `PolarSettings` `{ appId, webhookUrl, connected, hasAccessToken, sandbox, products, webhookEndpointId, lastNotificationAt, lastSync, events }`; `400` for non-web apps.
- `PUT /apps/:id/polar` (`manage`) `{ webhookSecret?: string|null, accessToken?: string|null, products?: { <Polar product id>: <product id> }, sandbox?: boolean, createWebhook?: boolean }` → `PolarSettings` (secrets stored encrypted). With an organization access token and no secret, Revflare creates (or re-keys) the webhook endpoint in Polar and keeps its secret; `400 { error }` when Polar refuses.
- `POST /apps/:id/polar/sync` (`manage`) `{ maxPages? }` → `{ orders, stored, error? }`: imports past orders with the access token.
- `POST /polar/webhooks/:key` (public; Standard Webhooks `webhook-id` / `webhook-timestamp` / `webhook-signature`, 5-minute tolerance, `whsec_` or legacy raw secrets): `order.paid` / `order.updated` / `order.refunded` → transactions, `subscription.*` → subscription state. `200 { ok, duplicate?, ignored? }`, `401` bad signature, `404` unknown key, `503` no secret yet (Polar retries). Events are stored with `source` `polar` (imports: `polar_poll`).
- `Transaction.store` `polar`, `source` `polar`; `Overview.topApps[].platform` `web`.

## Metrics (`read`)

Common query parameters: `apps=id1,id2` (default all), `currency=EUR` (default the workspace's), and for ranges `range=7d|28d|30d|90d|12m|mtd|ytd|all` or `from=YYYY-MM-DD&to=YYYY-MM-DD` (inclusive, UTC days).

- `GET /overview` → `Overview`: today and yesterday (UTC days; `tzOffset` = minutes east of UTC gives the caller's local days, from the transactions), KPIs with 28-day sparks and change (`mrr`, `revenue_28d`, `proceeds_28d`, `active_subscriptions`, `active_trials`, `new_customers_28d`, `trial_conversion_28d`, `churn_rate_28d`), 28-day MRR movement, revenue at risk, 30-day forecast, goals with progress, record day/month, top apps, open alerts.
- `GET /charts/:metric?range&interval=day|week|month&groupBy=app|country|product` → `Chart` (points, total, previousTotal, optional `series`). Metrics: `revenue, proceeds, mrr, mrr_proceeds, arr, active_subscriptions, active_trials, new_subscriptions, renewals, one_time_purchases, trials_started, trial_conversions, trial_conversion_rate, refunds, refunds_amount, refund_rate, churn_rate, churned_subscriptions, new_customers, arppu`. Rates are fractions. Interval defaults by range length.
- `GET /mrr-movement?range&interval` → `MrrMovement`.
- `GET /breakdown?metric&by=app|country|product&range&limit` → `Breakdown` (stock metrics use the current snapshot).
- `GET /transactions?limit&cursor&kinds=trial,conversion,new,renewal,one_time&country&product&q&refunded=true&environment=Production|Sandbox|all&source=apple_ads|google_ads|referral|organic|unknown` → `Page<Transaction>` with `currency`. Each transaction has `attribution` (`AdsAttribution`, see [Apple Ads attribution](#apple-ads-attribution-revflarekit)). `source` filters by it: the walk down the workspace's time index (`transactions(workspace_id, purchased_at)`) looks at 500 transactions at most per request, each joined by primary key to `install_links` and `attributions`; when they hold fewer than a page of matches, the page is short (possibly empty) and `nextCursor` continues after the last one looked at. The day totals (`days`) follow the filter. Subscription rows (every kind but `one_time`) carry `autoRenew`, the subscription's current auto-renew state (one lookup per page by the unique `subscriptions(app_id, original_transaction_id)` index): a trial with `autoRenew: false` that has not expired yet is a cancelled trial. Each row also has `sinceInstallMs` (on the customer's first purchase / trial, when its RevflareKit install time is known and earlier: ms since the install, else `null`), `cancelledAfterMs` (subscription rows: ms from this purchase to the first time auto-renew was turned off within its period, else `null`) and `quick` (either one within `QUICK_ACTION_MS` = 5 minutes, inclusive); these come from primary-key probes and one seek in the partial index `idx_events_cancel_original` (cancellation events only) per row of the page. `quick=true` keeps only quick rows: like `source`, at most 500 rows looked at per request (short pages continue through `nextCursor`), and no `days` totals.
- `GET /transactions?cancellations=true` (same `apps`, `country`, `product`, `q` (transaction / original transaction id), `environment`, `source`, `quick`, `limit`, `cursor`, `tzOffset`) → the cancellations stream: `Page<Transaction>` rows of `kind: "cancellation"`, one per stored auto-renew-off event (App Store `DID_CHANGE_RENEWAL_STATUS` / `AUTO_RENEW_DISABLED`, Google Play `SUBSCRIPTION_CANCELED`), newest first: `id` = event id, `purchasedAt` = when auto-renew was turned off (signed date), `customerId` / `expiresAt` from the subscription, `price` / `proceeds` 0, `autoRenew: false`, `sincePurchaseMs` (ms since the subscription's latest transaction at or before it), `purchaseKind` (that transaction's kind, `trial` = a cancelled trial), `quick` (`sincePurchaseMs` ≤ 5 minutes). Read through the partial index `idx_events_cancel` (workspace, signed date; cancellation events only). `days` counts cancellations per local day (`revenue` / `sales` 0); none with `source` / `quick`. `upcoming=true` is empty.
  Transactions whose `purchasedAt` is in the future (renewals Apple bills ahead of the new period) are left out until then and are listed with `upcoming=true` (oldest first). The response has `days`: totals of every day the page touches (`revenue`, `proceeds`, `sales`, `count`), in local days when `tzOffset` (minutes east of UTC) is given. Day metrics count a sale once its time has come.
- `GET /customers/:id` → `Customer` (`attribution`: the `AdsAttribution` of the install of the customer's first linked transaction, `source: "unknown"` when none is linked; `refundDataConsent`: whether Revflare may answer Apple's refund requests for this customer). Transactions have `refundPercentage` (100 for a full refund, e.g. 40 for a prorated one; `null` when not refunded): a prorated refund only takes its share out of revenue and proceeds. `events` (`CustomerEvent[]`: `{ type, subtype, at, productId, environment, transactionId }`) is the Apple notification history of the customer's subscriptions and purchases (by original transaction id, newest first, at most 100; Production only unless the customer is sandbox-only). Google Play events are the RTDN types (`SUBSCRIPTION_PURCHASED`, `SUBSCRIPTION_RENEWED`, `SUBSCRIPTION_CANCELED`, … `ONE_TIME_PRODUCT_PURCHASED`, `VOIDED_PURCHASE`). Each subscription has `autoRenewOffAt`: when auto-renew was turned off (signed date of the latest `DID_CHANGE_RENEWAL_STATUS` / `AUTO_RENEW_DISABLED`, or Google Play's `SUBSCRIPTION_CANCELED`), `null` while auto-renew is on; a `trial` / `active` / `grace` / `billing_retry` subscription with `autoRenew: false` is cancelled and ends at `expiresAt`; `cancelledAfterMs` = ms from the subscription's latest transaction at or before `autoRenewOffAt` to it. Activity: `firstSeenAt` (ms) = the earliest of the RevflareKit install time and the first transaction (`firstSeenSource`: `install` | `purchase`); `lastSeenAt` = the latest of the app's activity (the newest key event of the linked installs, their last report), the transactions (never after now) and the store notifications (`lastSeenSource`: `app` | `purchase` | `notification`); `installedAt` = install time of the earliest linked install (`installedAtSource`: `device` = first launch recorded by RevflareKit, `first_report` = its first report), `null` when none is linked. Installs come from `install_links` of the customer's original transaction ids and the `appAccountToken` (at most 20; key events read for the 5 most recent, one index row each). `timing` (`CustomerTiming`): `firstPurchaseAt` / `firstPurchaseKind`, `installToPurchaseMs` (install → first purchase or trial start, `null` without an earlier install time), `purchaseToCancelMs` / `cancelledAt` (the fastest purchase / trial start → auto-renew off), `purchaseToRefundMs` / `refundedAt` (the fastest purchase → refund), `quickPurchase` / `quickCancel` (within 5 minutes, inclusive). The first transaction carries `sinceInstallMs`. Everything is read per customer (their transactions, subscriptions and events), nothing scans the workspace.
- `PUT /customers/:id/refund-consent` (`manage`) `{ consent: boolean }` → `{ id, refundDataConsent }`: `false` = the customer withdrew their consent to share consumption data with Apple (their refund requests are skipped); `404` for customers of other workspaces.
- `GET /at-risk?limit` → `AtRisk` (billing retry, grace period, auto-renew off).
- `GET /forecast?days=30` → `Forecast`.

- Goals (`read` for reads, `manage` for writes; worker/lib/goals.ts). A goal is a target for a metric over a period on an app scope:
  - `metric`: money `revenue`, `proceeds`, `mrr` (targets in the workspace currency, stored in USD) or counts `new_subscriptions`, `trials_started`, `active_subscriptions`, `sales` (new subscriptions + renewals + one-time purchases). `kind`: `flow` metrics add up over the period; `stock` metrics (`mrr`, `active_subscriptions`) are a level (today's value).
  - `period`: `week` (Monday–Sunday), `month` (default), `quarter`, `year` (rolling: they start over) or `custom` with `startDate` / `endDate` (YYYY-MM-DD, inclusive, at most 731 days; it ends). Periods are UTC days.
  - `scope`: `all`, `include` (the `appIds`, at least one) or `exclude` (every app of the workspace but the `appIds`, at least one; apps added later count). App ids must be the workspace's (`400` otherwise).
  - `name` (optional, ≤ 60 characters; `label` is the name or a generated English one such as "Revenue · 3 apps"), `archived` (hidden from the overview, kept), `sortOrder` (manual order), `notify` (push to the workspace's devices when reached, once per period; app builds with `pushVersion` ≥ 4; `false` when omitted, the web and iOS apps and the CLI default it to `true`; a goal reached in the last minutes of a period still notifies during the first hour of the next UTC day).
  - `GET /goals` → `{ currency, items: GoalProgress[] }`: every goal, archived ones too (`archived: true`), in their order, with progress. `GET /goals/:id` → `{ currency, goal }`.
  - `GoalProgress` = `Goal` + `periodStart`, `periodEnd`, `periodLabel` (`2026-10`, `2026-Q4`, `2026`, `2026-W44`, `2026-10-01..2026-12-31`), `status` (`upcoming`|`active`|`ended`), `daysTotal`, `daysElapsed` (today included), `daysLeft` (whole days after today), `current` (flow: the period's total so far; stock: today's value), `startValue` (stock: the value at the start of the period, else null), `progress` (current / target), `projected` (flow: end-of-period value at the current pace; stock: the current value), `expected` (a linear path's value today; stock: from `startValue` to the target), `delta` (current − expected: ahead > 0, behind < 0), `pace` (`upcoming`|`on_track`|`behind`|`reached`|`missed`), `requiredPerDay` (still needed per remaining day, today included; 0 once reached, null once ended), `reachedAt` (first day at or over the target), `previous` (rolling goals: `{ periodStart, periodEnd, periodLabel, value, reached }` of the period before, against the current target; null for custom). Progress never depends on the `apps` filter of the request. Older fields stay: `appId` (the app of a one-app include scope, else null), `projected`, `periodLabel`.
  - `POST /goals` `GoalInput` `{ name?, metric, target, period?, startDate?, endDate?, scope?, appIds?, notify?, archived? }` (`appId` alone = include that app, for older clients) → `201 { id, currency, goal }`. Up to 100 goals per workspace.
  - `PATCH /goals/:id` any subset of `GoalInput` → `{ id, currency, goal }`. Changing what is measured (metric, target, period, dates, scope, apps) lets the goal notify again this period; the same app set in another order, or the target sent back as shown (converted at today's rate, rounded to cents), is no change. Only the `appIds` / `appId` of the body are checked: apps deleted since the goal was saved leave it on any edit (an include goal left without apps reads 0, labelled "No apps").
  - `POST /goals/reorder` `{ ids: [...] }` (the new order; goals left out follow in their order) → `{ ok, ids }`. `DELETE /goals/:id`.
  - `Overview.goals` lists the non-archived goals with the same progress, whatever the overview's `apps` filter.
- Alerts: `GET /alerts` → `{ items: Alert[] }` (last 100) `{ id, appId, kind, funnelId?, experimentId?, severity, title, body, createdAt, resolvedAt }`; kinds `notifications_silent`, `sync_failing`, `revenue_drop`, `refund_spike`, `events_silent`, `funnel_anomaly`, `release_regression` (the last two carry `funnelId`; [funnels.md](funnels.md#alerts)), `experiment_result` (an experiment reached P(best) ≥ 95% on its primary metric with the guardrails met; carries `experimentId`), `key_events_capped` (an app reached its daily key-event cap or the background budget: the rest of that UTC day is sampled; [funnels.md](funnels.md#exact-key-events)), `google_play_test` (info: Google's test notification arrived). `POST /alerts/:id/resolve`.

## Apple Ads attribution (RevflareKit)

- `POST /sdk/v1/report` (public; header `X-Revflare-Key: <app sdkKey>` or `sdkKey` in the body) `{ installId: UUID, attributionToken?, originalTransactionIds?: [..], appVersion?, environment?: "production"|"sandbox"|"xcode" }` → `SdkReportResponse` `{ ok: true, attribution: "pending"|"resolved"|"failed", source: "apple_ads"|"organic"|"unknown", campaignId: string|null, adGroupId: string|null, keywordId: string|null }` — RevflareKit sends the AdServices token once per install and the original transaction ids the install owns. Purchases made with `appAccountToken = installId` link themselves. Tokens are resolved with Apple right away and retried by the cron (Apple can answer 404 for a while; tokens expire after 24 h). `source`: `apple_ads` when Apple attributed the install (ids set), `unknown` while the token waits for Apple (`pending`), `organic` otherwise (resolved without attribution, no token, failed, expired) — the same rule as LTV's source; the SDK sends it back on `/sdk/v1/config` for remote config conditions. A token-less re-report with nothing new (no new transaction ids) writes nothing. `environment` (missing or invalid = `production`) is kept from the install's first report (`attributions.environment`; NULL for installs reported before it = production, filled by their next report) but only moves toward production: an install that later reports `production` (TestFlight → App Store build) becomes production and counts from then on, never the other way: `xcode` installs link no transaction ids and their token is never sent to Apple; `sandbox` / `xcode` installs and the app's test devices (`/apps/:id/test-devices`) are left out of attributed revenue, coverage, LTV and Meta sending.
- RevflareKit Android (Google Play apps) reports `{ installId, platform: "android", orderIds?: ["GPA.1234-5678-9012-34567", …], purchaseTokens?: [..] (≤ 90), installReferrer?: { referrer: "utm_source=…&utm_medium=…&utm_campaign=…&gclid=…", clickTs?, installTs? }, appVersion?, installedAt?, environment?: "production"|"sandbox"|"debug" }`. Order ids are accepted with or without the renewal suffix (`..N` is stripped: install links are by base order id = `original_transaction_id`); purchase tokens link through the stored subscriptions (`subscriptions.purchase_token`, known once the purchase's RTDN arrived). Purchases made with `obfuscatedAccountId` = install id link themselves (like `appAccountToken`). The install referrer is stored once (`utm_source`, `utm_medium`, `utm_campaign`, `gclid`, `referrer_click_at`; `clickTs` / `installTs` in seconds or milliseconds) and sets the install's source: `google_ads` (a `gclid`), `referral` (a `utm_source` other than Play's organic `google-play`), else `organic`. `debug` (debuggable build) is test data like `xcode`: nothing is linked. Remote config `source` rules accept `google_ads` and `referral` too.
- `GET /apps/:id` → `sdkKey`; `POST /apps/:id/sdk-key` rotates it (`manage`).
- `GET /revenue/attributed?range&apps|appleAppIds&currency&includeTest=true` (`read`) → `AttributedRevenue`: per day, app, Apple Ads campaign / ad group / keyword id with `campaignName` / `adGroupName` / `keywordName` (null when unknown: clients show `#<id>`): revenue, proceeds, transactions, trials, installs, payers; `coverage` = `installs` reporting, `attributed` (never test attribution) and `testInstalls` (installs with Apple's test attribution in the range). Default: production installs and purchases only; test attribution, sandbox / Xcode builds and test devices left out. `includeTest=true` counts them too (and sandbox purchases), rows of test installs flagged `test: true`, response `includeTest: true`.
- Test attribution: Apple's AdServices test payload (`campaignId` / `adGroupId` / `orgId` 1234567890, `keywordId` 12323222, what development and TestFlight builds get) marks the install `attributions.test_attribution = 1` when it resolves (migration 0022 marked existing ones). Such installs are left out of attributed revenue, coverage, LTV and Meta sending (Meta: like sandbox, sent only with Sandbox sending on) unless a read asks for test data; `/sdk/v1/report` and remote config conditions keep treating them as `apple_ads` (to test hard paywalls for Apple Ads users).
- `AdsAttribution` (`Transaction.attribution`, `Customer.attribution`) `{ source: "apple_ads"|"google_ads"|"referral"|"organic"|"unknown", test: boolean, campaignId, campaignName, adGroupId, adGroupName, keywordId, keywordName }` (strings or null): the RevflareKit install linked to the purchase (`install_links` by original transaction id, else `appAccountToken` = install id) and what Apple said: `unknown` = no install linked or the token still waits for Apple; `organic`; `apple_ads` with ids and names (`test: true` for Apple's test attribution).
- Apple Ads names: `GET /attribution/names` (`read`) → `{ names: [{ kind: "campaign"|"adgroup"|"keyword", id, name }] }`; `PUT /attribution/names` (`manage`, API keys allowed: Adsflare, `revflare attribution names import`) `{ names: [{ kind, id, name }] }` (at most 1000; ids are Apple Ads ids (digits, numbers accepted); an empty name deletes; the last entry of an id wins) → `{ updated, deleted }`: only names that change are written (unchanged ones cost one read each). Names resolve in every attribution read: the feed, customers, `/revenue/attributed` and the remote config pickers.
- `POST /sdk/v1/report` also records the country of the install's first report (Cloudflare's `request.cf.country`): the country of organic installs, which Apple gives none for. Optional `installedAt` (ms since epoch; RevflareKit 1.5.1+: its first launch, persisted on the device) is the install time for LTV, kept once when at most 30 days before the first report.

## LTV by acquisition source (RevflareKit installs, `read`)

Definitions in [ltv.md](ltv.md). Money is per install, refunds excluded (prorated refunds in part), in `currency` (default the workspace's).

- `GET /ltv?apps|appleAppIds&by=source|campaign|adgroup|keyword|country&cohort=day|week|month&range|from&to&currency` → `Ltv`: one row per install cohort (`cohort` = install day, Monday of the install week (default) or first of the month) × group: `installs`, `payers`, `trials`, `revenue` / `proceeds` to date, and `horizons` = D0 (first 24 hours), D7, D30, D90, D180 and to date (`day: null`) with `revenuePerInstall`, `proceedsPerInstall`, `payers`. A horizon the cohort has not fully reached is `{ immature: true }` with null values. `by` (default `source`): `apple_ads` / `organic`; Apple Ads campaign, ad group (`campaignId/adGroupId`), keyword (`campaignId/adGroupId/keywordId`, `none` for a missing id) with organic installs as one `organic` group; `country` (Apple's country, else the install's, else `unknown`). Range: install days (UTC), about 13 months back at most (`from` at most 396 days back, then the start of its cohort) (default 30 days for `cohort=day`, 26 weeks for `week`, 13 months for `month`); `from` moves to the start of its cohort. `coverage`: `installs` / `attributed` in the range, `preexisting` (installs whose purchases all started more than 48 h before the install: left out of installs and values), `payingCustomers` (the apps' customers whose first payment is in the range or later), `linkedCustomers` (of them, linked to a reporting install by a purchase that counts) and `share`. `summary=1` adds `summary`: the `/ltv/summary` rows for the same installs (one request for both tables).
- `GET /ltv/summary?apps|appleAppIds&by=campaign&range=90d|from&to&currency` → `LtvSummary`: one row per group (default `by=campaign`): `installs`, `payers`, `trials`, `conversion` (payers / installs), `revenue` / `proceeds` to date and `horizons` D0…D180 pooled over the install days old enough for each horizon (`installs` = how many installs that is; none → `immature: true`, null values). Pick a range longer than the horizon you need (D90 needs installs at least 91 days old: `range=180d`).

### For Adsflare (payback, ROAS)

Adsflare calls with its workspace API key, `appleAppIds=<App Store ids>` and `by=campaign|adgroup|keyword`, then joins rows on `campaignId` / `adGroupId` / `keywordId` (Apple Ads ids). Cohorts are UTC install days, while Apple Ads reports use the campaign's time zone: compare over whole weeks or longer ranges. Values are cached for the UTC day. With its spend and installs per group: predicted D30 revenue = `installs × horizons[D30].revenuePerInstall` (use `proceedsPerInstall` for net ROAS); D30 ROAS = that / spend; payback = the first horizon where `proceedsPerInstall ≥ spend / installs` (CPI). Check `horizons[i].installs` (sample size) and `coverage.share` (below ~0.8, linked revenue is incomplete: older app versions without RevflareKit, purchases not linked to an install) before acting on a group.

## Meta Ads (Conversions API)

Purchases go server-side to Meta's Conversions API as app events (guide: `docs/meta-ads.md`).

- `POST /sdk/v1/identifiers` (public; header `X-Revflare-Key: <app sdkKey>` or `sdkKey` in the body) `{ installId: UUID, fbAnonId?: string|null, idfa?: UUID|null, idfv?: UUID|null, attStatus: "authorized"|"denied"|"restricted"|"notDetermined"|"unavailable", bundleId?, appVersion?, appBuild?, osVersion?, deviceModel?, locale?, timeZone?, extinfo?: [16 strings] }` → `{ ok: true }`; `400` on bad input (UUID formats, lengths: fbAnonId ≤ 128, versions ≤ 32, deviceModel / timeZone ≤ 64, locale ≤ 35, bundleId ≤ 200; extinfo exactly 16), `404` unknown key. A zeroed IDFA / IDFV counts as missing. Stored per (app, install) with the caller's IP (`cf-connecting-ip`) and user agent; the latest call wins. RevflareKit sends it at launch and when the ATT status, the Facebook anonymous id or the app version changes. RevflareKit Android sends `platform: "android"`, the Google advertising id as `gaid` (stored like an IDFA: Meta's `madid`) and `limitAdTracking` instead of `attStatus` (`true` → `denied`, else `authorized`); no IDFV. Events of Android apps carry extinfo version `a2` (unless the SDK sends its own 16 fields) and no `vendor_id`.
- `GET /apps/:id/integrations/meta` (`read`) → `MetaIntegration` `{ enabled, datasetId, accessTokenSet, testEventCode, sendSandbox, sendWithoutAtt, events: { trial_started|initial_purchase|trial_converted|renewal|non_subscription_purchase: { enabled, name, defaultName } }, stats: { pending, sent, skipped, failed }, lastSentAt, lastError, backfilledAt }`. The access token is never returned. Purchases of test installs (sandbox / Xcode builds, test devices) are skipped ("Test install") unless `sendSandbox`. `/sdk/v1/identifiers` accepts `environment`; `xcode` and `debug` bodies are answered `{ ok: true }` and not stored.
- `PUT /apps/:id/integrations/meta` (`manage`) partial `MetaIntegrationUpdate` `{ enabled?, datasetId?, accessToken?, testEventCode?, sendSandbox?, sendWithoutAtt?, events?: { <type>: { enabled?, name? } } }` → `MetaIntegration`. `accessToken` is write-only (stored encrypted); `""` / `null` clears `datasetId`, `accessToken`, `testEventCode`; an event `name: null` restores the default. Event names: letters, digits, `_`, `-`, spaces, ≤ 40 characters. `enabled: true` needs a dataset id and a token (`400`). Turning it on the first time queues the last 7 days (as `.../backfill`).
- `POST /apps/:id/integrations/meta/test` (`manage`) → `{ ok: true, status, response }` (Meta's JSON): one `initial_purchase` test event (synthetic ids, value 0.99 USD) with the test event code; `400` without a test event code / dataset / token, `502 { error, status, response }` when Meta refuses it.
- `GET /apps/:id/integrations/meta/log?limit` (`read`) → `{ items: MetaDelivery[] }`: the last 100 deliveries, newest first (`eventType`, `eventName`, `eventId`, `transactionId`, `status` sent / skipped / failed, `httpStatus`, `response` trimmed to 500 characters with `fbtrace_id`, `reason`, `at`).
- `POST /apps/:id/integrations/meta/backfill` (`manage`) → `{ queued }`: queues the app's Apple transactions of the last 7 days (Production; Sandbox too when `sendSandbox`), at most 2,000; failed and skipped ones are queued again, sent ones never. `429 { code: "budget" }` when today's background budget is used up.

Mapping (ledger kind → event, default name, value in USD = `gross_usd`): `trial` → `trial_started` (`StartTrial`, 0); `new` → `initial_purchase` (`Subscribe`); `conversion` → `trial_converted` (`Subscribe`); `renewal` → `renewal` (`Subscribe`); `one_time` → `non_subscription_purchase` (`Purchase`). Refunds, cancellations and expirations are not sent; refunded transactions are skipped.

Request: `POST https://graph.facebook.com/<GRAPH_VERSION>/<datasetId>/events` (`GRAPH_VERSION` in `worker/lib/meta.ts`), body `{ data: [...], partner_agent: "revflare", access_token, test_event_code? }`, header `X-Forwarded-For` = the install's IP when the batch has one. Each event: `event_name`, `event_time` (purchase time, seconds), `action_source: "app"`, `event_id` = `custom_data.order_id` = `<transactionId>_<eventType>`, `user_data { anon_id?, madid?, external_id: sha256 hex of the Revflare customer id (else the original transaction id), client_ip_address?, client_user_agent? }`, `app_data { advertiser_tracking_enabled: 1 when ATT is authorized else 0, application_tracking_enabled: 1, vendor_id?, extinfo }` (the SDK's 16 fields, else `["i2", bundleId, appVersion, appBuild, osVersion, deviceModel, locale, "", "", "0", "0", "0", "0", "0", "0", timeZone]`), `custom_data { currency: "USD", value, order_id, content_type: "product", content_ids: [productId], contents: [{ id: productId, quantity: 1 }] }`.

Gating (skips are logged with their reason): integration off or event type off; Sandbox transaction with `sendSandbox` off; refunded; older than 7 days; no install linked (`install_links` by original transaction id, or the transaction's `appAccountToken`) or no identifiers for it — events wait up to 24 h for both (checked with back-off: 2, 4, 8 ... minutes, then hourly); ATT not `authorized` with `sendWithoutAtt` off; neither `anon_id` nor IDFA. Delivery: the cron (every 5 minutes, its own database call) sends up to 100 due events per app in one request (a few apps, at most 10 requests per run). `429` / `5xx` / network errors retry after 1 min, 5 min, 15 min, 1 h, 2 h, 4 h, 6 h (8 tries in all), then fail. Other `4xx`: Meta rejects the whole batch for one bad event, so a rejected batch of several events is retried one event per request and only the bad one fails with Meta's message; token / permission errors (`401`, `403`, code 190, 10, 2xx) fail the batch at once (fix the token, then backfill).

## Refund requests (Apple CONSUMPTION_REQUEST)

When a customer asks Apple for a refund, the App Store sends a `CONSUMPTION_REQUEST` notification and accepts consumption information for 12 hours. Revflare answers it with the app's In-App Purchase key (guide: `docs/refund-requests.md`).

- `GET /apps/:id/integrations/refunds` (`read`) → `RefundRequestSettings` `{ source: app|workspace|none, enabled, consentAttested, consentAttestedAt, consentAttestedBy, refundPolicy, declineAfterDays, sampleContentProvided, consumptionPercent, deliveryStatus: "DELIVERED", notifications: { status, forwarded, lastNotificationAt }, stats: { pending, sent, skipped, failed, expired }, lastSentAt, lastError }`.
- `PUT /apps/:id/integrations/refunds` (`manage`) partial `RefundRequestSettingsUpdate` `{ useDefaults?, enabled?, consentAttested?, refundPolicy?: none|decline|decline_if_delivered_after_days|grant_prorated|grant_full, declineAfterDays?: 1-3650|null, sampleContentProvided?, consumptionPercent?: 0-100|null }` → `RefundRequestSettings`. `enabled: true` needs the consent attestation (`consentAttested: true`, stored with the user and time; `400` otherwise); `consentAttested: false` withdraws it and turns answers off. `decline_if_delivered_after_days` needs `declineAfterDays`. An app without its own settings starts from the workspace defaults; `useDefaults: true` deletes the app's own settings (the defaults apply again).
- `GET /integrations/refunds/defaults` (`read`) → `RefundRequestDefaults` `{ enabled, consentAttested, consentAttestedAt, consentAttestedBy, refundPolicy, declineAfterDays, sampleContentProvided, consumptionPercent, apps: { total, usingDefaults } }`; `PUT` (`manage`) takes the same body as an app (but `useDefaults`) → `RefundRequestDefaults`. Every App Store app without its own row uses them, new apps included.
- `GET /apps/:id/integrations/refunds/log?limit` (`read`) → `{ items: RefundRequestLogItem[] }`: the last 100 requests, newest first (`receivedAt`, `dueAt`, `transactionId`, `originalTransactionId`, `productId`, `productName`, `environment`, `requestReason` = Apple's `consumptionRequestReason`, `status` pending / sent / skipped / failed / expired, `attempts`, `request` = the body sent, `httpStatus` = Apple's (202 accepted, 0 network error), `response` trimmed, `reason`).

Which requests: `CONSUMPTION_REQUEST`s Apple delivers to the app's Revflare notification URL (also when Revflare forwards them, `forwardNotificationUrl`: the other server may not answer), and those seen through Notification History polling while still inside Apple's 12 hours (older polled ones are not queued). One row per notification id. Production requests that go unanswered (off / no attestation, failed, expired, retrying on missing setup) raise a `refund_request_unanswered` alert per app and day (resolved by the next accepted answer) and, with `STUDIOFLARE_URL` + secret `STUDIOFLARE_API_KEY`, a Studioflare note. Skips (logged with the reason): answers off, no consent attestation, the customer withdrew consent, Xcode / local testing environment. A request is `expired` once Apple's 12 hours (from the notification's `signedDate`) have passed.

Request: `PUT https://api.storekit.itunes.apple.com/inApps/v2/transactions/consumption/{transactionId}` (Sandbox: `api.storekit-sandbox.itunes.apple.com`), JWT of the workspace's In-App Purchase key (`appstore_iap`), body (`ConsumptionRequest` v2): `customerConsented: true`, `deliveryStatus: "DELIVERED"` (Revflare cannot know about delivery problems), `sampleContentProvided`, optional `refundPreference` and optional `consumptionPercentage` (milliunits: `consumptionPercent` × 1000; consumables, non-consumables and non-renewing subscriptions only — never for auto-renewable subscriptions). Policy: `none` sends no preference; `decline` sends `DECLINE` at any age; `decline_if_delivered_after_days` sends `DECLINE` when the purchase (for a subscription: its original purchase) is at least `declineAfterDays` days old, else none; `grant_full` → `GRANT_FULL`; `grant_prorated` → `GRANT_PRORATED` (for other products than auto-renewable subscriptions only with a `consumptionPercent` strictly between 0 and 100, else no preference). Delivery: tried right after the notification, then by the cron every 5 minutes (its own database call, at most 5 requests a run). `429` / `5xx` / network errors and a missing In-App Purchase key or bundle id retry after 1, 5, 15, 30 min, 1, 2, 4 h (a `429`'s `Retry-After` when longer) while the 12 hours last (then `expired`); other errors fail with Apple's message (`400` invalid body, `401` key, `404` unknown transaction).

## Promotional offers

Guide: `docs/offers.md`. Promotional offers are signed with the workspace's In-App Purchase key (`appstore_iap`); win-back offers need no signature.

- `POST /sdk/v1/offers/sign` (public; header `X-Revflare-Key: <app sdkKey>`) `{ installId, productId, offerId, appAccountToken?: UUID, environment?: "production"|"sandbox"|"xcode" }` (every environment is signed; the log row records it) → `200` `OfferSignature` `{ productId, offerId, keyId, nonce, timestamp, signature, jws }`, `Cache-Control: no-store`. `nonce`: a new lowercase UUID; `timestamp`: ms. `signature` (legacy, `Product.PurchaseOption.promotionalOffer(offerID:keyID:nonce:signature:timestamp:)` / `SKPaymentDiscount`): base64 DER ECDSA P-256 SHA-256 over `bundleId ⁣ keyId ⁣ productId ⁣ offerId ⁣ appAccountToken (lowercase, or empty) ⁣ nonce ⁣ timestamp` (U+2063 separators). `jws` (iOS 18.4+, `promotionalOffer(_:compactJWS:)`): header `{ alg: ES256, kid: keyId, typ: JWT }`, claims `{ iss: issuerId, iat (s), aud: "promotional-offer", bid, nonce, productId, offerIdentifier, appAccountToken? (lowercase, when sent) }`, no `exp`. Errors: `400` bad body or no key; `404` unknown key; `403 { code: "offer_not_allowed" }` when (productId, offerId) is not a promotional entry of the app's allowlist, or in strict mode when the install has no linked subscription in the product's group; `409 { code: "not_configured" }` without an In-App Purchase key or bundle id; `429 { code: "rate_limited" }` + `Retry-After` over 10 signatures / hour per install or 1000 / hour per app (per Worker isolate). App, allowlist and key come from the isolate's cache (60 s); signatures are always logged, refusals (403 / 409) are sampled (the first 20 an hour per app and isolate, then 1 in 50 with its `count`), the last ~1000 rows per app (`offer_signatures`, trimmed every 50 rows); logging is background work and stops when the day's background budget is used up (signing does not). Bodies over 4 KB: `413`.
- `GET /apps/:id/offers` (`read`) → `OfferSettings` `{ appId, offers: [{ productId, offerId, label, kind: promotional|win_back }], strict, keyConfigured, bundleId, sdkKey, updatedAt }`.
- `PUT /apps/:id/offers` (`manage`) partial `{ offers?: [{ productId, offerId, label?, kind? (default promotional) }], strict?: boolean }` → `OfferSettings`. `offers` replaces the list (at most 200; duplicates: the last wins). Only `promotional` entries are signed; `win_back` entries label redemptions.
- `POST /apps/:id/offers/import` (`manage`) → `OfferImportResult` `{ added, found, errors, settings }`: adds the promotional (`offerCode`) and win-back (`offerId`) offers of the app's subscriptions from the App Store Connect API (`/v1/subscriptions/{id}/promotionalOffers`, `/winBackOffers`; the first 15 subscriptions). `409` without an App Store Connect key or App Store id, `502` on App Store Connect errors.
- `GET /apps/:id/offers/log?limit` (`read`, default 100, at most 1000) → `{ items: [{ at, installId, productId, offerId, status: signed|not_allowed|not_configured|not_subscribed, count, environment }] }` (`environment`: the build that asked, null for rows logged before it was sent), newest first (`count` > 1: a sampled refusal row standing for that many answers).
- `GET /apps/:id/offers/stats?range=90d` (`read`; `range` / `from` / `to` like the charts) → `OfferStats` `{ appId, from, to, currency, totals: { redemptions, revenue, proceeds }, items: [{ offerType: 2|4, offerTypeLabel, offerId, productId, label, redemptions, customers, revenue, proceeds }] }`: Production transactions with Apple `offerType` 2 (promotional) or 4 (win-back) bought in the range (refunds take their share out).
- `GET /apps/:id/lapsed?days=90` (`read`, 1-730) → `LapsedSegment` `{ appId, days, from, to, currency, total, byProduct: [{ productId, productName, count }], items }`: Production subscriptions with status `expired` and auto-renew off that expired in the window (grace period, billing retry, refunded and revoked ones excluded, and customers with a current subscription in the app: active, trial, grace or billing retry); `items` (at most 200, latest first): `{ customerId, originalTransactionId, productId, productName, expiredAt, country, totalPaid }` (`totalPaid`: the customer's revenue).
- `Transaction` (feed, customer) carries `offerType` (1 introductory, 2 promotional, 3 offer code, 4 win-back) and `offerId`; `offer` reads e.g. `"free trial"`, `"win-back"`, `"promotional (pay as you go)"`.

## Offerings and placements (paywalls)

Per app: offerings (identifier, display name, free-form `metadata` JSON for the paywall, ordered packages `{ identifier, productId, metadata }`), at most one **current** offering, and placements (paywall locations → an offering, or `null` = the current one). RevflareKit loads them at launch, so paywall products change without an app update (`sdk/ios/README.md`). Identifiers (offerings, packages, placements): `^[A-Za-z0-9_.$-]{1,64}$`; suggested package identifiers `$weekly`, `$monthly`, `$two_month`, `$three_month`, `$six_month`, `$annual`, `$lifetime`. Limits per app: 50 offerings, 20 packages per offering, 50 placements, 8 KB per metadata object, 512 KB for the whole config. Invalid input is a `400` and changes nothing.

- `GET /sdk/v1/offerings` (public; header `X-Revflare-Key: <app sdkKey>`; optional `If-None-Match`, optional `?appVersion=` accepted and ignored for now) → `200` `SdkOfferings` with `ETag: "<version>"`, `Cache-Control: max-age=60`; `304` (no body) when `If-None-Match` has the current version; `400` without a key; `404` unknown key. Body:
  ```json
  { "version": "3f9a1c0b7d2e", "currentOfferingId": "default",
    "offerings": [ { "identifier": "default", "displayName": "Default", "metadata": { "title": "Go Pro" },
                     "packages": [ { "identifier": "$annual", "productId": "com.example.app.annual", "metadata": {} } ] } ],
    "placements": { "onboarding": "default", "settings": null } }
  ```
  `version` is a short hash of this payload: it changes with every edit that changes what the SDK gets. An app without offerings gets `currentOfferingId: null`, `offerings: []`, `placements: {}`. Cost: answers come from the Worker isolate's memory or the Cache API (60 s); the database is read at most once a minute per isolate (one indexed read). Changes made through the API reset this data center's cache at once; elsewhere they show within 60 s.
- `GET /apps/:id/offerings` (`read`) → `OfferingsConfig` `{ currentOfferingId, offerings: Offering[] (identifier, displayName, metadata, packages, isCurrent, createdAt, updatedAt; in display order), placements: [{ identifier, offeringId|null }], version, updatedAt, preview }` (`preview`: the exact `/sdk/v1/offerings` body).

Changes (`manage`) answer with the new config plus `warnings: string[]` (`OfferingsChange`): a package whose `productId` is not one of the app's known products (synced from App Store Connect or seen in sales) is saved with a warning, not refused.

- `PUT /apps/:id/offerings` `OfferingsInput` `{ currentOfferingId?, offerings: [{ identifier, displayName?, metadata?, packages?: [{ identifier, productId, metadata? }] }], placements?: [{ identifier, offeringId }] | { <placement>: offeringId|null } }` — replaces the whole config atomically (`revflare offerings <app> apply`). The `GET` output can be sent back as is (`isCurrent: true` on an item works when `currentOfferingId` is missing). `currentOfferingId` and placements must point at offerings in the body.
- `POST /apps/:id/offerings` `OfferingInput` `{ identifier, displayName?, metadata?, packages?, isCurrent? }` → `201`; `409` if the identifier exists. The first offering becomes current unless `isCurrent: false`.
- `PATCH /apps/:id/offerings/:identifier` partial `{ identifier?, displayName?, metadata?, packages?, isCurrent? }` (`packages` replaces the list; renaming updates the current offering and placements; `isCurrent: false` leaves no current offering) → `200`; `404` unknown offering; `409` when renaming onto an existing one.
- `DELETE /apps/:id/offerings/:identifier[?force=true]` → `200`; `409` while placements use it unless `force` (they then fall back to the current offering). Deleting the current offering leaves none current.
- `POST /apps/:id/offerings/:identifier/current` → makes it the (only) current offering; `404` unknown offering.
- `PUT /apps/:id/placements/:identifier` `{ offeringId: "<offering>" | null }` → `201` new / `200` updated; `404` unknown offering. `DELETE /apps/:id/placements/:identifier` → `200`; `404` unknown placement.

## Entitlements and non-renewing durations

Per app, served to RevflareKit 1.9+ inside `GET /sdk/v1/offerings` (same row, same cache and `ETag`; older SDKs ignore the fields):

- **Entitlements**: entitlement → product ids. RevflareKit merges them with the app's own map (union per entitlement; the app's map always applies, also offline) and loads those products too, so a new product (e.g. `com.example.app.pass_3day`) unlocks `pro` without an app update.
- **Durations** of non-renewing products (passes): `{ unit: day | week | month | year, count: 1…1000 }`. StoreKit / Google Play give these transactions no expiry: RevflareKit computes it (purchase + duration on the UTC calendar, months clamp to the last day of the month; repeat purchases of the same product stack: each one starts at the later of its purchase and the current expiry; refunded / revoked ones are left out). Revflare stores `expires_at = purchase + duration` on every one-time transaction of the product (Apple `Non-Renewing Subscription` and any other non-subscription product with a duration, Google Play one-time products included; no stacking server-side), so customer histories show when each pass ends. Setting, changing or removing a duration recomputes the product's stored transactions (`updatedTransactions`; removing clears their expiry): day / week / removal at once in one statement; month / year 5,000 transactions per change, the rest continued in the background by the cron within the daily budget (`truncated: true`). Passes stay one-time revenue: never MRR, active subscriptions or churn.
- **Never on lifetime products or subscriptions**: a duration is refused (`400`) for a product known (product catalog or stored sales) as non-consumable or auto-renewable; stored non-consumable sales never get an expiry, and RevflareKit applies durations only to non-renewing subscriptions on iOS (non-consumables are always lifetime). Google Play one-time products are ambiguous (Play stores them all as one-time): a duration is allowed with a warning; never set one on a lifetime product.
- **App-declared products are protected**: RevflareKit ignores a server duration for a product the app lists itself (its entitlement map, product ids or consumables) unless the app also sets a local duration for it, so a server configuration never takes access away from products the app shipped with. Server entitlements only add products (union).
- The dashboard's expiry is purchase + duration per transaction; RevflareKit stacks repeat purchases on the device, so a pass bought before the previous one ended expires later on the device than in the dashboard. A refunded pass in a stack is left out, so the passes after it start (and end) earlier. RevflareKit 1.9 against a server older than 1.9 gets no `entitlements` / `products` and uses the app's own map and durations only.

Identifiers: `^[A-Za-z0-9_.$-]{1,64}$`. Limits per app: 50 entitlements, 100 products per entitlement, 100 durations. Payload fields (each omitted when empty, so apps without entitlements keep their `version`):
```json
{ "version": "…", "currentOfferingId": "default", "offerings": [ … ], "placements": { … },
  "entitlements": { "pro": ["com.example.app.annual", "com.example.app.pass_3day"] },
  "products": { "com.example.app.pass_3day": { "duration": { "unit": "day", "count": 3 } } } }
```

- `GET /apps/:id/entitlements` (`read`) → `EntitlementsConfig` `{ entitlements: [{ identifier, productIds }], durations: [{ productId, unit, count }], updatedAt, preview }` (`preview`: the fields the SDK gets).

Changes (`manage`) answer `EntitlementsChange` = the new config + `warnings` (products not among the app's known products, durations stored on products that take none, Google Play one-time products with a duration, entitlements without products) + `updatedTransactions` + `truncated`:

- `PUT /apps/:id/entitlements` `EntitlementsInput` `{ entitlements?: { <name>: [productIds] } | [{ identifier, productIds }], durations?: { <productId>: { unit, count } | "3d" } | [{ productId, unit, count }] }` — replaces each part present, keeps the other.
- `PUT /apps/:id/entitlements/:entitlement` `{ productIds }` → sets its products (`201` when new). `DELETE /apps/:id/entitlements/:entitlement` → `200`; `404` unknown.
- `POST /apps/:id/entitlements/:entitlement/products` `{ productIds }` (or `{ productId }`) → adds (`201` creates the entitlement). `DELETE /apps/:id/entitlements/:entitlement/products/:productId` → `200`; `404` when absent.
- `PUT /apps/:id/durations/:productId` `{ unit, count }` or `{ duration: "3d" | "1w" | "1m" | "1y" }` → `201` new / `200` updated; `400` for a known non-consumable or auto-renewable product. `DELETE /apps/:id/durations/:productId` → `200`; `404` when absent.

## Remote config (like Firebase Remote Config)

Per app: typed parameters with a default value and values per condition; conditions are ordered (priority = order: for each parameter the first matching condition that has a value wins, else the default) and match when all their rules match. Model, evaluation and caching: `docs/remote-config.md`. Types: `RemoteConfig*` in `shared/types.ts`.

- Parameter `{ key, type: "string"|"number"|"boolean"|"json", description?, defaultValue?, useInAppDefault?, conditionalValues: { <condition>: <typed value> | { "useInAppDefault": true } } }`. Keys `^[A-Za-z0-9_.-]{1,128}$`. `defaultValue` is required unless `useInAppDefault: true` (the key is then left out of the device's values and the app's own default applies). Numbers must be finite; numbers and booleans may be sent as strings (`"1"`, `"true"`). Each value ≤ 32 KB of JSON.
- Condition `{ name, color?, rules: Rule[], unsupported?, expression? }`. Names `^[A-Za-z0-9_ .-]{1,64}$`; `color` one of `blue brown cyan deep_orange green indigo lime orange pink purple teal`. An empty `rules` list always matches; `unsupported: true` (imported from Firebase, original `expression` kept) never matches. Rules:
  - `{ type: "country" | "ip_country" | "storefront", values: ["CN", ...] }` (ISO alpha-2; alpha-3 accepted and converted). `country` = the storefront the SDK sent, else the request's country (Cloudflare); `ip_country` = the request's country; `storefront` = only the SDK's storefront.
  - `{ type: "language", values: ["zh", "en_us"] }` (language of the device locale; a value with a region matches that locale), `{ type: "locale", values: ["zh_cn"] }` (`-` and `_` are the same, case-insensitive).
  - `{ type: "app_version" | "app_build" | "os_version" | "sdk_version", op: ">=" | ">" | "<=" | "<" | "==" | "!=", value: "2.1.0" }` (numeric per part: 2.10 > 2.9; missing parts are 0; a device without the value never matches).
  - `{ type: "percent", from: 0, to: 20, seed? }`: bucket = first 4 bytes of sha256(lowercase installId + seed) scaled to [0, 100); matches `from <= bucket < to`; seed defaults to the condition name; no installId → no match.
  - `{ type: "install_id", values: ["<uuid>", ...] }` (testers).
  - `{ type: "source", values: ["apple_ads" | "organic" | "unknown", ...] }` (the install's acquisition source the SDK sends; a device that sends none matches no `source` rule).
  - `{ type: "apple_ads_campaign" | "apple_ads_ad_group" | "apple_ads_keyword", values: ["1234567890", ...] }` (Apple Ads ids, digits, up to 20; numbers accepted).
  - `{ type: "environment", values: ["production" | "sandbox" | "xcode", ...] }` (the build; devices that send none are `production`).
- Limits per app: 300 parameters, 50 conditions, 20 rules per condition, 300 values per list rule, 512 KB for the whole config. Conditional values must reference existing conditions. Invalid input is a `400` and changes nothing.

- `GET /sdk/v1/config?installId=<uuid>&appVersion=2.1&appBuild=12&osVersion=18.1&locale=zh_CN&storefront=CN&sdk=1.5.0&source=apple_ads&campaign=123&adGroup=456&keyword=789&environment=production` (public; header `X-Revflare-Key: <app sdkKey>`; optional `If-None-Match`) → `200` `SdkRemoteConfig` with `ETag: "<version>"`, `Cache-Control: private, max-age=60`; `304` (no body) when `If-None-Match` has this device's current version; `400` without a key; `404` unknown key. All query parameters are optional; `source` (`apple_ads`|`organic`|`unknown`, from the `/sdk/v1/report` answer), `campaign` / `adGroup` / `keyword` (Apple Ads ids, `^\d{1,20}$`) and `environment` (`production`|`sandbox`|`xcode`, default `production`) feed the `source`, `apple_ads_*` and `environment` rules; invalid values are ignored. Body:
  ```json
  { "version": "a1b2c3d4e5f6",
    "values": { "onboarding_version": "v1", "max_free_accounts": 1, "show_discounted_paywall": true, "paywall": { "title": "Go Pro" } },
    "conditions": ["china"], "country": "CN",
    "experiments": [ { "id": "exp_3f9a1c2b7d10", "variant": "b", "keys": ["paywall"] } ] }
  ```
  `values` omits keys whose resolved value is the in-app default; `conditions` lists every condition the device matches, in priority order; `country` is the one `country` rules used (null if unknown). `experiments` (left out when the device is in none) lists the running or stopped [experiments](#experiments-ab-tests-on-remote-config) the device is enrolled in: its variant and the parameter keys the experiment sets (their values in `values` are the variant's); RevflareKit sends `experiment_exposure` when the app reads one of these keys. Assignment needs `installId` and is computed in the Worker from the install id and the experiment id (no database work). `version` is a hash of this response (values, matched conditions, country, experiment assignments): an edit that does not change what this device gets keeps its version, so its `If-None-Match` still gets a `304`. Cost: the app's compiled config comes from the Worker isolate's memory or the Cache API (60 s) and is evaluated in the Worker; the database is read at most once a minute per isolate (one indexed read). Changes made through the API reset this data center's cache at once; elsewhere they show within 60 s.
- `GET /apps/:id/config` (`read`) → `RemoteConfig` `{ conditions, parameters, version, updatedAt, warnings }` (`version`: short hash of the config, changes with every edit; `warnings`: unsupported or unused conditions).
- `PUT /apps/:id/config` (`manage`) `RemoteConfigInput` `{ conditions?, parameters: [...] | { <key>: { type, defaultValue, ... } } }` → `RemoteConfig`: replaces the whole config atomically (`revflare config <app> apply`). The `GET` output can be sent back as is.
- `POST /apps/:id/config/import-firebase[?dryRun=true][&merge=true]` (`manage`), body = a Firebase Remote Config template (`firebase remoteconfig:get`, REST API `GET .../remoteConfig`: `{ conditions: [{ name, expression, tagColor? }], parameters: { <key>: { defaultValue: { value } | { useInAppDefault: true }, conditionalValues: { <condition>: { value } }, valueType, description } }, parameterGroups: { <group>: { parameters: {...} } } }`) → `RemoteConfigImport` (`RemoteConfig` + `dryRun`, `merged`, `imported: { parameters, conditions, unsupportedConditions }`; `warnings` lists everything not imported as is). Parameter groups are flattened; condition names with characters Revflare does not allow are renamed (`20% rollout` → `20_ rollout`, warning); `valueType` STRING / NUMBER / BOOLEAN / JSON maps to the types (values that do not parse make the parameter a string, with a warning); personalization and rollout values become the in-app default (warning). Supported condition terms, combined with `&&`: `device.country in [...]`, `device.language in [...]`, `device.os == 'ios'` (always true; other OSes unsupported), `app.id == '...:ios:...'` (always true), `app.version.>=(['2.1.0'])` / `app.build.<(['120'])` (all six operators and `exactlyMatches` with one value), `percent <= N`, `percent > N`, `percent between A and B`, `percent('seed') ...`, `true`, `false`. Anything else (user properties, audiences, dates, `||`, `!`, regex matches, Firebase installation ids) → the condition is imported with `unsupported: true` (never matches) and a warning; the import does not fail. `dryRun` returns the result without saving; by default the config is replaced, `merge` keeps the current config and merges parameters by key and conditions by name (imported ones win; new conditions are appended, lowest priority).
- `GET /apps/:id/config/attribution-options?days=30` (`read`; 1-90) → `AttributionOptions` `{ appId, days, campaigns: [{ id, name, installs }], adGroups: [{ id, campaignId, name, installs }], keywords: [{ id, campaignId, adGroupId, name, installs }] }`: Apple Ads ids of the app's production installs Apple attributed in the window (at most 200 each, by installs) for condition pickers; `name` from `PUT /attribution/names` (null when unknown). Cached until the data version or the UTC day changes (setting names changes it).
- `POST /apps/:id/config/evaluate` (`read`) `{ installId?, appVersion?, appBuild?, osVersion?, locale?, storefront?, ipCountry?, sdkVersion?, source?, campaign?, adGroup?, keyword?, environment? }` → `RemoteConfigEvaluation`: the exact SDK body for that device plus `parameters: { <key>: { condition: <name>|null, useInAppDefault, value? } }` (which condition each value came from; null = the default; `experiment` / `variant` when the value comes from an experiment's variant, then `condition` is null) and `experiments` as in the SDK body. The web app's "Preview as".
- Config changes that would break an active (running or stopped) experiment are refused with `400`: removing one of its parameters or changing its type, removing or renaming its targeting condition.

## Experiments (A/B tests on remote config)

Per app: an experiment gives each variant its own values for 1 to 10 remote config parameters and compares trials, paid conversions and revenue per install of the installs exposed to each variant. Model, assignment, metrics and statistics: [experiments.md](experiments.md). Types: `Experiment*` in `shared/types.ts`.

- `Experiment` `{ id, appId, name, hypothesis, keys, variants: [{ id, name, weight, values }], targeting, traffic, primaryMetric, status, startedAt, stoppedAt, endsAt, rolledOutVariant, createdAt, updatedAt }`. Variants: 2 to 5, ids `a`..`e` in order, `a` = control; weights (percent, > 0) sum to 100; `values` maps keys to typed values (as the parameter's type; the control may leave keys out to keep the device's current value, the other variants set every key; no `useInAppDefault`). `targeting`: the name of a remote config condition (only matching devices enroll; null = every device with an install id). `traffic`: percent of the matching devices enrolled (default 100). `primaryMetric`: `trial_started` | `paid` (default) | `revenue_per_install`. `status`: `draft` → `running` → `stopped` → `rolled_out`, or `archived` (from draft, running or stopped). `endsAt` = `startedAt` + 90 days: the cron stops a running experiment then.
- `GET /apps/:id/experiments` (`read`) → `{ items: Experiment[] }` (newest first); `GET /apps/:id/experiments/:eid` → `Experiment`.
- `POST /apps/:id/experiments` (`manage`) `ExperimentInput` `{ name, keys, variants: [{ id?, name?, weight?, values }], targeting?, traffic?, primaryMetric?, hypothesis? }` → `201` `Experiment` (a draft). Weights may be left out on every variant (even split). Keys must exist in the app's remote config. At most 100 experiments per app (`409`).
- `PATCH /apps/:id/experiments/:eid` (`manage`) partial `ExperimentInput` → `Experiment` (drafts only, else `409`). `DELETE /apps/:id/experiments/:eid` → `{ ok: true }` (not while running or stopped: `409`, archive it first).
- `POST /apps/:id/experiments/:eid/start` (`manage`) → `Experiment` (`running`): the draft is validated again against the current config; `409` when one of its parameters is already in another running or stopped experiment. Devices get their variant at their next config fetch (the SDK cache of this data center is reset at once, elsewhere within 60 s).
- `POST /apps/:id/experiments/:eid/stop` (`manage`) → `Experiment` (`stopped`): devices keep their variant (no flip back) until rollout or archive; the next results are final.
- `POST /apps/:id/experiments/:eid/rollout` (`manage`) `{ "variant": "b" }` (running or stopped) → `Experiment` (`rolled_out`): the variant's values become the parameters' defaults (conditional values stay; keys the control leaves out keep their default) and the experiment leaves the SDK payload. `400` unknown variant.
- `POST /apps/:id/experiments/:eid/archive` (`manage`) → `Experiment` (`archived`): leaves the payload without changing the config.
- `GET /apps/:id/experiments/:eid/results` (`read`) → `ExperimentResults` `{ experimentId, status, primaryMetric, currency, from, to, daysRunning, variants: [{ variant, name, weight, exposed, trials, trialRate, paid, paidRate, revenue, proceeds, revenuePerInstall, proceedsPerInstall, probabilityBest: { trial_started, paid }, lift: { trial_started, paid } }], enoughData, reasons, confident, exposureSource: "events"|"snapshot"|"none", approximate, notes, daily: [{ day, variant, exposed }], frozen, generatedAt }`. `exposed`: installs that sent `experiment_exposure` for the variant since the start; trials: trials started after the first exposure; paid: first paid transactions (a subscription's first paid period, bought or converted from a trial, or a non-subscription purchase) after the first exposure; revenue / proceeds: every transaction (renewals included) of subscriptions and purchases begun after the first exposure (Production, refunds subtracted, workspace currency); see docs/experiments.md#metrics. `probabilityBest`: P(best) from Beta posteriors (seeded Monte Carlo); `lift`: against the control `{ expected, low, high }` (relative, 95% credible interval; null for the control). `enoughData` is false (and `reasons` says why) until the experiment has run 7 days, every variant has 100 exposed installs and the primary metric 10 conversions. `confident` `{ variant, probability }`: P(best) ≥ 95% on the primary metric with the guardrails met (also raises an `experiment_result` alert). `approximate` + `notes`: sampled events, more than 20,000 exposed installs per experiment (spread over the variants), or exposures from the daily snapshot. The stored results are served: the cron recomputes a running experiment's results every 6 hours, a read computes them only when none are stored yet (or once more after the stop, then `frozen`); every computation counts against the daily background budget, and once it is used up the stored results come back with a note (or none yet: zeros and the reason). A draft answers zeros (`reasons: ["The experiment has not started."]`). Without event queries (`CF_ACCOUNT_ID`, `CF_ANALYTICS_TOKEN`) the results fall back to the daily snapshot (exposures only, a note says so); `502 { code: "analytics_query_failed" }` when the SQL API fails.
- `POST /apps/:id/experiments/:eid/results/refresh` (`read`) → `ExperimentResults`, recomputed now: at most once an hour per experiment (`429 { error, retryAfter }` + `Retry-After` before that, or when today's background budget is used up), `409` once the results are final.

## Events and funnels (RevflareKit events, Workers Analytics Engine)

App events are stored in a Workers Analytics Engine dataset (binding `EVENTS`, dataset `revflare_events`); key events are also stored in the database ([funnels.md](funnels.md#exact-key-events)). They are queried through the Analytics Engine SQL API with `CF_ACCOUNT_ID` (var) and `CF_ANALYTICS_TOKEN` (secret, Account → Account Analytics → Read). How funnels are computed: `docs/funnels.md`.

- `POST /sdk/v1/events` (public; header `X-Revflare-Key: <app sdkKey>`) body:
  ```json
  { "installId": "<uuid>", "appVersion": "1.0", "appBuild": "1", "osVersion": "18.1", "locale": "en_US", "environment": "production",
    "events": [ { "id": "<uuid>", "name": "paywall_view", "ts": 1792400000123, "sessionId": "<uuid>", "props": { "placement": "onboarding" } } ] }
  ```
  → `200 { ok: true, accepted, dropped }`. At most 200 events per request (`413`, also for bodies over 1 MB). Event `name`: `^[A-Za-z0-9_.:-]{1,64}$`; `id` / `sessionId`: letters, digits and `-`, at most 64 (`sessionId` optional); `ts`: milliseconds, at most 7 days old and 1 hour ahead of the server; `props`: at most 10, keys `^[A-Za-z0-9_.-]{1,40}$`, values strings ≤ 100 characters (numbers and booleans are stored as strings, `null` is ignored). Invalid events (and repeated ids within the batch) are dropped and counted, they do not fail the batch. `400` bad body / installId not a UUID / no key, `404` unknown key, `429` with `Retry-After` (seconds) when an install sends more than ~1,000 events in a burst (refills 2 per second) or an app more than ~50,000 (1,000 per second). Without the `EVENTS` binding the request still answers `200` (`accepted: 0`, everything dropped). Cost: no database work for a batch without key events (the SDK key is cached in the isolate for 5 minutes, unknown keys for 1 minute; the "last event received" note is written at most every 10 minutes per isolate and app). Key events ([funnels.md](funnels.md#exact-key-events)) are also stored in the database after the response (one database call: `INSERT OR IGNORE` by `(app_id, id)`, so retries never double-write; at most 500 per install and UTC day and the app's daily cap, within the daily background budget; about 3 rows written per new event plus 2 per request); a database failure is logged, never returned.
  Data point per event (`index1` = app id): `blob1` name, `blob2` install id (lowercase), `blob3` session id, `blob4` app version, `blob5` app build, `blob6` OS version, `blob7` country (Cloudflare's, from the request), `blob8` locale, `blob9` event id, `blob10` workspace id, `blob11` props JSON, promoted props `blob12` placement, `blob13` offering, `blob14` product, `blob15` step, `blob16` screen, `blob17` variant, `blob18` environment (`production`|`sandbox`|`xcode`; top-level `environment` of the body, missing or invalid = `production`); `double1` event time (ms), `double2` received time (ms), `double3` layout version (2; events of layout 1 have no `blob18` and count as production).
- Test data ([funnels.md](funnels.md#test-data)): reads count production events (`blob18 = 'production'`, or layout 1 events: `double3 < 2`) from other devices than the app's test devices; `includeTest=true` on the events summary and funnel reports counts everything. Experiments, alerts, insights and the digest always use production data only.
- `GET /apps/:id/key-events` (`read`) → `KeyEventSettings` `{ appId, builtin: string[], patterns: string[], dailyCap, dailyCapIsDefault, defaultDailyCap, backgroundWritesPerDay, writesPerEvent, retentionDays, since: "YYYY-MM-DD"|null, today: { date, count, capped }, limits }`; `PUT /apps/:id/key-events` (`manage`) `{ patterns?: string[], dailyCap?: 0..1000000 | null, retentionDays?: 7..365 }` → `KeyEventSettings` (`400` on an invalid pattern, more than 20 patterns or unknown fields). Built-in key events (case-insensitive): `first_open`, `purchase_*`, `restore_*`, `paywall_view`, `paywall_close`, `onboarding_*`, `experiment_exposure`; extra patterns are event names with at most one `*` at the start or the end (`*_paywall_view`, `promo_*`), effective from the next UTC day for exact reads. `dailyCap` (the cap in effect; `null` in a PUT = the instance's default `defaultDailyCap` = min(50,000, `backgroundWritesPerDay` / `writesPerEvent` / 2), 9,166 with the Free plan defaults; `0` = store none): over it the rest of the UTC day is Analytics Engine only and one `key_events_capped` alert is raised; `retentionDays` (default 180): older stored events are deleted by the cron. `since`: the first UTC day stored exactly (exact reads start there); `today.capped`: the day is incomplete (cap, background budget or a failed write). Other isolates pick changes up within 5 minutes.
- `GET /apps/:id/test-devices` (`read`) → `TestDevices` `{ appId, installIds: [uuid], limit: 50 }`; `PUT /apps/:id/test-devices` (`manage`) `{ installIds: [uuid] }` replaces the list (at most 50, lowercased, `400` on anything that is not a UUID). Test devices are left out of events, funnels, experiments, insights, LTV, attributed revenue and Meta sending.
- `GET /apps/:id/analytics/status` (`read`) → `AnalyticsStatus` `{ ingest, query, dataset, missing: string[], lastEventAt, lastTestEventAt, sdkKey }` (`lastEventAt`: the last production event, what the event-silence alert reads; `lastTestEventAt`: the last sandbox / Xcode event; `ingest`: the `EVENTS` binding exists; `query`: `CF_ACCOUNT_ID` and `CF_ANALYTICS_TOKEN` are set; `missing` says what to add).
- `GET /apps/:id/events/summary?range=7d[&includeTest=true]` (`read`; `1d`..`92d`) → `EventSummary` `{ from, to, days, totalEvents, uniqueInstalls, events: [{ name, count, installs, lastSeenAt, source }], daily: [{ date, count, byEvent }], approximate, includeTest, notes }` (top 50 events; `daily` per UTC day with the top 8 events, the rest as `(other)`). `source: "exact"`: a key event stored for the whole range, counted from the database (exact count and unique installs); `"sampled"`: Analytics Engine (counts weighted by `_sample_interval`); both by UTC day of reception. `totalEvents` adds both; `approximate` when a sampled event was sampled. `notes`: why exact counts were not used (incomplete day, more than 150,000 stored key events) or that the daily breakdown hit its row limit.
- `GET /apps/:id/funnels` (`read`) → `{ items: Funnel[] }`; `GET /apps/:id/funnels/:fid` → `Funnel` `{ id, appId, name, steps, windowSeconds, ordered, alerts: { enabled, sensitivity }, createdAt, updatedAt }`.
- `POST /apps/:id/funnels` (`manage`) `FunnelInput` `{ name, steps, window?: "1h"|"1d"|"7d"|"30d"|…, windowSeconds?, ordered? }` → `201`. Steps (2 to 10): `{ type: "event", name, filters?: [{ key, value }], label? }` or `{ type: "revenue", kind: "trial_started"|"paid"|"any_purchase", label? }`; the first step is an event. Filters: equality, at most 5 per step, values ≤ 100 characters of letters, digits, spaces and `_ . : @ / + , # -` (the SQL API has no bind parameters). Window: 1 minute to 90 days (default 7 days). `ordered` defaults to `true`. At most 50 funnels per app (`409`). `alerts?: { enabled?: boolean, sensitivity?: "high"|"normal"|"low" }` (default on, normal; no other fields): the daily funnel anomaly / release regression checks ([funnels.md](funnels.md#alerts)).
- `PATCH /apps/:id/funnels/:fid` (`manage`) partial `FunnelInput` → `Funnel`; `DELETE /apps/:id/funnels/:fid` → `{ ok: true }`.
- `GET /apps/:id/funnels/:fid/report?range=30d|from=YYYY-MM-DD&to=YYYY-MM-DD&breakdown=[&includeTest=true]` (`read`) → `FunnelReport` `{ funnel, from, to, breakdown, steps: [{ index, label, users, conversionFromPrevious, conversionFromFirst, dropOff, medianSecondsFromPrevious }], groups: [{ value, steps }], approximate, source, notes, includeTest, generatedAt }`. `source: "exact"` when every event step is a key event stored for the whole range (no Analytics Engine query, not sampled); otherwise `"sampled"` (Analytics Engine for every step; a note says when exact data starts after the range start, a day was capped, or the breakdown is `os_version` / `locale`, which only Analytics Engine has). `from` / `to`: entry days (first step), UTC, at most 92 days. `breakdown`: `app_version`, `os_version`, `country`, `locale`, `placement`, `offering`, `product`, `step`, `screen`, `variant` (value at the first step; top 10 plus `(other)`). Cached 5 minutes.
- Analytics errors: `409 { code: "analytics_not_configured" }` without `CF_ACCOUNT_ID` / `CF_ANALYTICS_TOKEN`; `502 { code: "analytics_query_failed" }` when the SQL API fails (e.g. a token without Account Analytics Read).

## App Store acquisition (Apple App Analytics)

Where App Store visitors, downloads and App Store purchases come from, from Apple's App Analytics reports (Analytics Reports API): source type (`App Store search` — Apple Ads included —, `App Store browse`, `Web referrer`, `App referrer`, `App Clip`, `Notification`, `Unavailable`, ...), referrer (Source Info: the referring app or website) and campaign token (`ct=` in an App Store link such as `https://apps.apple.com/app/id<APPID>?pt=<provider token>&ct=<campaign>`).

Revflare keeps one ONGOING report request per app. Creating it needs an App Store Connect key with the **Admin** role; reading the reports works with Sales and Reports or Finance. Apple produces the first reports 1–2 days after the request, then daily; each day is complete after 2–3 days (newer instances replace earlier ones). The cron imports new report instances a few apps at a time (each app at most every 6 hours) within the background budget; new apps get a request at 01:xx UTC.

Revflare imports the **Standard** reports (complete counts by source type) and the **Detailed** ones (adds referrer and campaign): in Detailed reports Apple leaves out rows with fewer than 5 users and adds a little noise, so referrer / campaign groups sum to less than the totals. Devices, OS versions, territories and page types are aggregated away. Purchases are Apple's estimate by the source of the download, in USD converted to the requested currency; Revflare cannot tie individual customers to a campaign.

- `GET /acquisition?range&apps&by=source|referrer|campaign|day|app&currency&limit` (`read`) → `Acquisition` `{ currency, from, to, by, level: "standard"|"detailed", totals, rows, firstDay, lastDay }`. `by` takes several dimensions (`by=day,source`); default `source`. Metrics per row: `impressions`, `impressionsUnique`, `pageViews`, `pageViewsUnique`, `downloads` (first-time), `redownloads`, `conversionRate` (downloads / unique page views; `null` without views), `purchases` (refunds subtract), `proceeds`, `sales`. `firstDay: null` = no reports imported yet.
- `GET /acquisition/campaigns?apps` (`read`) → `{ currency, items: AcquisitionCampaign[] }`: campaign tokens seen (all time) per app with first / last day, impressions, page views, downloads, redownloads, purchases, proceeds.
- `GET /acquisition/status?apps` (`read`) → `{ items: AcquisitionStatus[] }`: per app `state` (`none`, `requested` = waiting for Apple's first reports, `producing`, `stopped` = Apple stopped it after inactivity (renewed automatically), `failed`), `requestId`, `requestedAt`, `checkedAt`, `reports` found, `lastProcessingDate`, `firstDay`, `lastDay`, `error`.
- `POST /acquisition/requests` `{ appIds?, limit? (default 10, max 100), retry? (default true: failed / stopped apps again) }` (`manage`) → `{ created, existing, failed: [{ appId, name, error }], remaining }`: reuses the app's ONGOING request at Apple or creates one. Call again while `remaining > 0`.
- `POST /acquisition/sync` `{ appIds? }` (`manage`) → `{ apps, requests, instances, rows, more, budget?, rateLimited?, errors }`: one bounded import round now.
- `POST /imports/acquisition` (`manage`) → job `acquisition`: requests for every app, then every report instance Apple has.
